A trained [[vla]] policy usually arrives with the stack it was trained in: PyTorch, the repo's preprocessing, its own action head. A robot has to run it next to sensing and control, on the processor and memory the robot already has. vla.cpp is a C++ runtime that serves eleven policies through one server and one bundle format, treating PyTorch as a conversion-time tool rather than a runtime dependency. What the policies share moves into the runtime; what they differ in stays in a small model adapter.

The runtime splits into three layers <Cite id="vla-cpp-paper" where="§III" />. **Model adapters** define each policy's computation: its attention pattern, its conditioning path and its action generation. **Hardware backends** execute the shared tensor operations. The **client** owns sensing and control — tokenization, normalization, command mapping, replay — and it may be Python; model execution is C++ <Cite id="vla-cpp-paper" where="§III-C" />.

A policy ships as GGUF: weights, architecture metadata and the normalization statistics in one bundle, with vision weights in a companion file. The C++ server holds the weights and answers synchronous requests over ZeroMQ with Protocol Buffers; requests carry images, token ids, state and optional noise or masks, and responses carry the chunk, its dimensions and timings <Cite id="vla-cpp-paper" where="§III-C" />. A new policy adds an adapter, a converter and a runtime registration; the server, the protocol and the client do not change <Cite id="vla-cpp-paper" where="§III-C" />.

Eleven policies run on that one interface: SmolVLA, Evo-1, π0, π0.5, GR00T-N1.5/1.6/1.7, VLA-JEPA, VLA-Adapter, OpenVLA-OFT and BitVLA <Cite id="vla-cpp-paper" where="Fig. 1, Table I" />. Coverage is uneven — BitVLA's ternary path is CUDA-only and OpenVLA-OFT was profiled on Metal and OpenVINO alone <Cite id="vla-cpp-paper" where="Table I" />. What varies per policy is exactly what an adapter must preserve: attention patterns, conditioning, masks and where the state token sits <Cite id="vla-cpp-paper" where="§III-B" />.

## Two action heads, one interface

An observation $o = (I_{1:V}, \ell, s)$ is $V$ camera images, a tokenized instruction $\ell$ and the robot state $s$. A policy turns it into a chunk $A \in \mathbb{R}^{H \times d_a}$: $H$ actions of $d_a$ command dimensions. The client executes the first $S$ of them, with $1 \le S \le H$, before observing again <Cite id="vla-cpp-paper" where="§III-A" />. That split is [[action-chunking]], and both head styles below return through it.

Iterative heads compute observation conditioning $C = F_\theta(o)$, start from a noise chunk $X^0$ and refine it with $T$ Euler steps <Cite id="vla-cpp-paper" where="§III-A, Eq. 1" />:

$$
X^{k+1} = X^k + (\tau_{k+1} - \tau_k)\, v_\theta(X^k, \tau_k, C, s)
$$

$\tau$ is an integration schedule, not physical time, and $v_\theta$ is the learned [[flow-matching]] velocity field. Each checkpoint keeps its own convention: SmolVLA and π0 integrate from 1 to 0, GR00T-N1.7 from 0 to 1, and Evo-1 starts from uniform noise; reversing the direction means flipping the sign of the velocity <Cite id="vla-cpp-paper" where="§III-A" />.

BitVLA, OpenVLA-OFT and VLA-Adapter skip the loop and regress the chunk directly, $A = R_\theta(o)$ <Cite id="vla-cpp-paper" where="§III-A" />. Both paths return a chunk and its dimensions through the same interface, so the client does not know which kind it is driving.

In an iterative head the observation tokens form a prefix and the candidate-action tokens a suffix, and only the suffix changes from step to step. The runtime computes the prefix once per request and reuses its keys, values and projections across all $T$ steps <Cite id="vla-cpp-paper" where="§III-B" />.

π0 caches each layer's prefix keys and values for joint attention; SmolVLA alternates joint and cross attention and caches the cross-attention projections; GR00T-style heads cache backbone features for a separate action transformer <Cite id="vla-cpp-paper" where="§III-B" />. That is [[observation-reuse]], the same prefix idea as a [[kv-cache]], applied to one request: the cache is thrown away when the next observation arrives <Cite id="vla-cpp-paper" where="§III-B" />.

With conditioning time $P$ and expert-step time $E$, model latency is approximately $L_{\text{model}}(T) \approx P + T\,E$, against $T(P + E)$ if conditioning were recomputed at every step; the idealized speedup is $T(P+E)/(P+TE)$, between 1 and $T$ <Cite id="vla-cpp-paper" where="Eq. 3" />.

The sweep shows the fixed part staying put. On GR00T-N1.7 the vision stage takes 18.5 to 18.9 ms at every step count, while backbone-plus-head time grows from 19.6 ms at one step to 107.5 ms at sixteen; the measured fit is 13.9 + 5.8T ms, or about 32.6 ms of fixed work plus 5.8 ms per step once vision is included <Cite id="vla-cpp-paper" where="§IV-E, Table VI" />.

Success stays between 95 and 99 of 100 across the sweep, so one to sixteen steps barely moves the task numbers on this benchmark <Cite id="vla-cpp-paper" where="Table VI" />. Caching does not remove the expert's cost: with prefix features already reused, the action expert still takes nearly half of SmolVLA's and GR00T-N1.6's execution time, and for BitVLA's direct head it is almost all of it <Cite id="vla-cpp-paper" where="§IV-E" />. A roofline analysis puts the prefix computation above both devices' ridge points while the small expert sits at low arithmetic intensity <Cite id="vla-cpp-paper" where="§IV-E, Fig. 3" />.

## Ternary execution on tensor cores

BitVLA's weights are scaled ternary, $q \in \{-1, 0, 1\}$, packed as four two-bit codes per byte <Cite id="vla-cpp-paper" where="§III-D" />. On CUDA the runtime quantizes each activation row to int8 around its largest magnitude, multiplies activations against the packed weights with integer matrix-multiply–accumulate instructions, accumulates in 32-bit integers, and converts to bfloat16 scaled by the row and output-group factors <Cite id="vla-cpp-paper" where="§III-D, Eq. 4" />. The baseline kernel uses dp4a dot products on CUDA cores; the multi-row path uses IMMA tensor-core instructions, adapting packed-weight techniques from Ladder, BitBLAS and bitnet.cpp <Cite id="vla-cpp-paper" where="§III-D" />.

Storage and arithmetic are separate wins. Packing shrinks the model file from 5.6 GiB to 1.34 GiB and the transient host allocation during loading from 11.1 GiB to 1.15 GiB without changing latency; replacing the kernel is what removes the time <Cite id="vla-cpp-paper" where="§IV-D" />. The packed path is also the paper's smallest deployment: the full policy completes 200 of 200 LIBERO-Object episodes on an 8 GB Jetson Orin Nano, at 2199 MiB peak process RSS <Cite id="vla-cpp-paper" where="Abstract, §IV-D" />.

Similar success rates do not establish numerical agreement. Different reference protocols, checkpoints or preprocessing can land near the same number while the actions differ; the paper checks numerical agreement separately, on fixed inputs <Cite id="vla-cpp-paper" where="§IV-B, §III-E" />.

Quantizing to Q4_0 takes the file from 6292.4 MB to 5134.8 MB, and 4556.0 MB with the vision tower quantized too; fixed inputs speed up 1.081× and 1.144×. Success falls from 196 of 200 at BF16 to 190 at Q4_0 — a 3.0-point drop with an approximate 95% interval of [−7.1, +0.8] <Cite id="vla-cpp-paper" where="§IV-D, Table V" />. The +V rows keep 195 of 200 at a similar relative error, so fixed-input error alone does not predict these outcomes <Cite id="vla-cpp-paper" where="§IV-D" />.

The SmolVLA case study makes the failure mode concrete. Its vision encoder turns image-patch coordinates into discrete indices that select learned position embeddings; a coordinate computed at a different precision can cross an index boundary and select a different embedding <Cite id="vla-cpp-paper" where="§IV-F" />. Matching the half-precision reference drops the position-embedding relative error from 0.32 to 0.003 and lifts LIBERO-Object task 0, placing a soup container in a basket, from 2/10 to 9/10 <Cite id="vla-cpp-paper" where="§IV-F" />.

The maximum action difference against the reference is about 1.97 after denormalization, concentrated on the gripper channel, and large enough to reverse the gripper command; matching index precision takes it below $10^{-2}$ <Cite id="vla-cpp-paper" where="§IV-F" />. GR00T-N1.6 uses interpolated position embeddings instead and scores 10/10 in both precision configurations <Cite id="vla-cpp-paper" where="§IV-F" />. On Metal, running the vision and language towers in 32-bit reduces the fixed-input discrepancy from 2.0e-3 to 8.3e-5, at a cost of 33 ms and 672 MiB <Cite id="vla-cpp-paper" where="§IV-F" />.

The prediction-check tool is the general recipe: it fixes weights, images, tokens, state, noise, masks, schedules and transforms, compares runtime actions with reference actions, and reports maximum absolute and relative RMS error so a discrepancy can be traced through intermediate tensors <Cite id="vla-cpp-paper" where="§III-E" />.

The execution horizon moves success more than the hardware did. With $H = 50$, success peaks at 49/50 at $S = 16$ and falls to 19/50 at $S = 50$, where the robot executes the full predicted chunk and replans only between chunks <Cite id="vla-cpp-paper" where="§IV-G" />. A controlled delay study on ALOHA holds at 9/10 or 10/10 for injected delays from 0 to 2000 ms, but ten episodes per condition cannot resolve changes near 100% fail rates <Cite id="vla-cpp-paper" where="§IV-G, Table VIII" />.

## What it reuses

- The [[vla]] policies themselves: trained in their own stacks, deployed as they are; vla.cpp only converts them <Cite id="vla-cpp-paper" where="§I" />.
- [[flow-matching]] for the velocity field the iterative heads integrate.
- The [[kv-cache]] idea, pointed at one request as [[observation-reuse]].
- [[action-chunking]] for the prediction and execution horizons every sweep reports.
- llama.cpp and ggml for the bundle format and the shared tensor execution <Cite id="vla-cpp-paper" where="§I, §III-C" />.

## The repository today

The released repository is ahead of the paper: its support matrix lists more policies (Octo-Small, TurboVLA, ACT) and a Hexagon backend for Snapdragon CPUs, GPUs and NPUs alongside the five backends the paper measured, and it publishes prebuilt binaries, Python bindings, conversion and quantization docs, and a walkthrough of each policy on ggml <Cite id="vla-cpp-repo" />. One practical warning from its robot guide: the client owns preprocessing, and selecting the wrong architecture at launch "loads, runs and returns plausible, wrong actions" <Cite id="vla-cpp-repo" where="README, Rollout on a real robot" />.
