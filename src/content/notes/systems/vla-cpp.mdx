A [[vla|VLA]] policy is trained in PyTorch, but a robot often can't run PyTorch, because its small computer is already busy with sensors and motor control. vla.cpp converts eleven such policies into one file format and serves them all from one C++ server, so PyTorch is needed only for the conversion <Cite id="vla-cpp-paper" where="Abstract, §I" />. It works because each policy splits in two. What every policy shares (loading weights, matrix math on each chip) lives in the runtime. What differs (the attention pattern, how actions are produced) lives in a small per-policy adapter.

Three more ideas follow that split: observation reuse, ternary weights, and checking that the converted policy computes the same actions.

The robot client sends three things: camera images, the instruction as token ids, and the robot's current state. The server runs them through the policy and sends back an action chunk, which is a short sequence of future actions, together with timings. The client then executes those actions on the robot <Cite id="vla-cpp-paper" where="§III-C" />.

The runtime has three layers, and each one has a single job <Cite id="vla-cpp-paper" where="§III" />:

1. A **model adapter** describes one policy's computation: which tokens attend to which, how the observation conditions the action head, and how actions are produced.
2. A **hardware backend** runs the tensor operations that every policy shares. The paper measures five backends: CUDA, Metal, CPU, SYCL and OpenVINO.
3. The **client** handles sensing and control: tokenizing the instruction, normalizing inputs, mapping actions to robot commands and replaying them. The client can be written in Python, because only model execution has to be C++ <Cite id="vla-cpp-paper" where="§III-C" />.

Each policy ships as a GGUF bundle, the file format of llama.cpp. The bundle holds the weights, the architecture metadata and the normalization statistics, and the vision weights go in a second file beside it <Cite id="vla-cpp-paper" where="§III-C" />. Because the server and the protocol are shared, adding a policy means writing an adapter, a converter and a runtime registration, and nothing else changes <Cite id="vla-cpp-paper" where="§III-C" />.

The paper runs eleven policies this way: SmolVLA, Evo-1, π0, π0.5, GR00T-N1.5, N1.6 and N1.7, VLA-JEPA, VLA-Adapter, OpenVLA-OFT and BitVLA <Cite id="vla-cpp-paper" where="Fig. 1, Table I" />. Not every policy runs on every backend, though. For example, BitVLA's ternary path exists only on CUDA <Cite id="vla-cpp-paper" where="Table I" />.

## Two kinds of action head

The eleven policies produce actions in two different ways, and the server has to serve both through one interface. Both kinds take the same input and return the same output. The input is an observation $o = (I_{1:V}, \ell, s)$: $V$ camera images, the instruction $\ell$ and the robot state $s$. The output is an action chunk $A \in \mathbb{R}^{H \times d_a}$, which means $H$ future actions, each with $d_a$ numbers (one per joint or gripper command).

The robot executes only the first $S$ actions, where $1 \le S \le H$, and then observes again <Cite id="vla-cpp-paper" where="§III-A" />. Predicting $H$ actions but executing $S$ of them is [[action-chunking]].

An **iterative head** starts from a random chunk and improves it step by step. It first turns the observation into conditioning features $C = F_\theta(o)$. Then it starts from a noise chunk $X^0$ and applies $T$ Euler steps, each one moving the chunk a little in the direction a learned velocity field $v_\theta$ points <Cite id="vla-cpp-paper" where="§III-A, Eq. 1" />:

$$
X^{k+1} = X^k + (\tau_{k+1} - \tau_k)\, v_\theta(X^k, \tau_k, C, s)
$$

Here $\tau$ is a position along the path from noise to actions, not physical time, and the velocity field is trained with [[flow-matching]]. The checkpoints don't agree on direction: SmolVLA and π0 go from $\tau = 1$ to $0$, while GR00T-N1.7 goes from $0$ to $1$. So an adapter that reverses the direction must also flip the sign of the velocity <Cite id="vla-cpp-paper" where="§III-A" />.

A **regression head** skips the loop and predicts the chunk in one pass, $A = R_\theta(o)$. BitVLA, OpenVLA-OFT and VLA-Adapter work this way <Cite id="vla-cpp-paper" where="§III-A" />. Since both heads return a chunk and its size through the same interface, the client never needs to know which kind of head it is talking to.

## Observation reuse keeps iterative heads cheap

<Calc

    { label: 'Share of latency spent in solver steps', expr: 'T * E / (P + T * E)', format: 'percent', role: 'op' },
  ]}
  note="Defaults are the paper's fit for GR00T-N1.7 on an RTX 3060: about 32.6 ms of fixed work and 5.8 ms per solver step. Raise T and watch the speedup grow, because the fixed work is paid only once."
/>

An iterative head runs its network $T$ times, but most of the input doesn't change between runs. The observation tokens (images, instruction, state) come first, as a prefix. The action tokens come after them, as a suffix. Only the suffix changes from one solver step to the next, so the runtime computes the prefix once per request and reuses its keys, values and projections at every step <Cite id="vla-cpp-paper" where="§III-B" />.

This is [[observation-reuse]]. It is the same idea as a [[kv-cache]], but it lives for one request only, because the next request brings a new observation <Cite id="vla-cpp-paper" where="§III-B" />.

What gets reused depends on the policy, which is why this logic lives in the adapter. π0 keeps each layer's prefix keys and values. SmolVLA keeps the projections its cross-attention layers read. GR00T-style heads keep the backbone features that feed a separate action transformer <Cite id="vla-cpp-paper" where="§III-B" />.

The calculator above shows the cost. Call $P$ the time to process the observation and $E$ the time for one solver step. With reuse, one request takes about $P + T\,E$. Without reuse, every step would process the observation again and take $T(P + E)$. The speedup is the ratio of the two, $T(P+E)/(P+TE)$, which is between 1 and $T$ <Cite id="vla-cpp-paper" where="Eq. 3" />.

The measurements match this model. The vision time stays near 18.5 ms whatever $T$ is, because the observation is processed once. The backbone-plus-head time grows by about 5.8 ms for each extra step <Cite id="vla-cpp-paper" where="§IV-E, Table VI" />. Success stays between 95 and 99 at every step count, so on this benchmark the number of steps barely affects the task <Cite id="vla-cpp-paper" where="Table VI" />.

Reuse removes the repeated observation work, but it can't make the steps themselves cheaper. Even with reuse, the action head still takes almost half of SmolVLA's and GR00T-N1.6's time <Cite id="vla-cpp-paper" where="§IV-E" />. The reason is that the action head is small, so it does little arithmetic for each byte it reads and is limited by memory bandwidth, not compute <Cite id="vla-cpp-paper" where="§IV-E, Fig. 3" />.

## Ternary weights: BitVLA on an 8 GB board

BitVLA's weights can only be $-1$, $0$ or $+1$, times a scale factor. A value with three choices fits in two bits, so the runtime packs four weights into each byte <Cite id="vla-cpp-paper" where="§III-D" />. To multiply, it first rounds each row of activations to 8-bit integers, using that row's largest value as the scale $\alpha_m$. It then multiplies the integer activations by the ternary weights on tensor cores, adds the products in 32-bit integers, and multiplies the result by the row scale $\alpha_m$ and the weight-group scale $\beta_g$ <Cite id="vla-cpp-paper" where="§III-D, Eq. 4" />.

Packing and the new kernel solve two different problems. Packing saves memory: the model file shrinks from 5.6 GiB to 1.34 GiB, and the memory needed while loading drops from 11.1 GiB to 1.15 GiB, but latency doesn't change <Cite id="vla-cpp-paper" where="§IV-D" />. The tensor-core kernel saves time, about four times on both boards in the table. Together they let the full policy run on an 8 GB Jetson Orin Nano, where it completes all 200 episodes using 2199 MiB of process memory at its peak <Cite id="vla-cpp-paper" where="Abstract, §IV-D" />.

A similar success rate does not mean the two implementations compute the same actions. Two policies can both succeed 96% of the time while their actions differ, so the paper checks numerical agreement separately, on fixed inputs <Cite id="vla-cpp-paper" where="§IV-B, §III-E" />.

## When a tiny precision change flips the gripper

  title="How SmolVLA's vision encoder picks a position embedding"

Most rounding errors stay small as they pass through a network, but this one doesn't, because it changes a choice instead of a value. SmolVLA's vision encoder turns each image patch's coordinate into an integer index and uses it to pick a learned position embedding. If the coordinate is computed at a slightly different precision, it can land on the other side of an index boundary, and the encoder picks a different embedding <Cite id="vla-cpp-paper" where="§IV-F" />.

On the robot this flipped the gripper. The largest action difference from the reference was about 1.97, mostly in the gripper channel, which is large enough to reverse the gripper command. When the runtime matched the reference's half precision for this step, the difference dropped below $10^{-2}$, and success on one LIBERO-Object task rose from 2 of 10 to 9 of 10 <Cite id="vla-cpp-paper" where="§IV-F" />. GR00T-N1.6 interpolates between embeddings instead of picking one, so it has no boundary to cross, and it succeeds 10 of 10 times at both precisions <Cite id="vla-cpp-paper" where="§IV-F" />.

Bugs like this are why the runtime ships a prediction-check tool. It fixes every input (weights, images, tokens, state, noise, masks and schedules), runs both the runtime and the PyTorch reference, and reports the largest difference and the relative RMS difference. When the actions differ, comparing the intermediate tensors shows where the difference starts <Cite id="vla-cpp-paper" where="§III-E" />.

Speed is not the main point of vla.cpp, and the table shows why. Against plain (eager) PyTorch, vla.cpp is up to 6.21× faster. ## On a real robot, the execution horizon matters most

The robot clients in the paper block: they send an observation, wait for the chunk, execute $S$ actions, and only then ask again. So the robot's real action rate depends on both the round-trip latency $L_{\text{rt}}$ and the time per action $\Delta t$, as $f_{\text{exec}} \approx S/(L_{\text{rt}} + S\,\Delta t)$ <Cite id="vla-cpp-paper" where="§IV-G, Eq. 6" />.

The execution horizon $S$ changed success far more than the hardware did. With chunks of $H = 50$ actions, success peaks at 98% when the robot executes 16 actions before replanning. It falls to 38% when the robot executes the whole chunk and replans only between chunks <Cite id="vla-cpp-paper" where="§IV-G" />. A likely reason (our reading, not the paper's) is that the last actions of a long chunk were planned from an observation that is many actions old. This tradeoff between fewer policy calls and fresher observations is the core of [[action-chunking]].

## What it reuses

- The [[vla|VLA]] policies themselves. They are trained in their own code, and vla.cpp only converts them <Cite id="vla-cpp-paper" where="§I" />.
- [[flow-matching]] for the velocity field that iterative heads follow.
- The [[kv-cache]] idea, applied within one request as [[observation-reuse]].
- [[action-chunking]] for the prediction horizon $H$ and execution horizon $S$.
- llama.cpp and ggml for the bundle format and the shared tensor operations <Cite id="vla-cpp-paper" where="§I, §III-C" />.

## The repository today

The released repository has moved past the paper. It lists more policies (Octo-Small, TurboVLA and ACT) and a Hexagon backend for Snapdragon chips, and it ships prebuilt binaries, Python bindings and a walkthrough of each policy <Cite id="vla-cpp-repo" />. Its robot guide gives one practical warning: the client does the preprocessing, so choosing the wrong architecture at launch "loads, runs and returns plausible, wrong actions" <Cite id="vla-cpp-repo" where="README, Rollout on a real robot" />.
