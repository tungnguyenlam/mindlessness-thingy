A language model generates one token at a time. To produce token $t$, every attention layer needs the keys and values of tokens $1 \dots t-1$. Those don't change once computed, so instead of recomputing them at every step, the model keeps them in memory. That memory is the KV cache.

## What it costs

For [[mha]], each layer stores one key and one value vector per head per token. In elements:

$$
\text{KV cache} = 2 \times n_\text{layers} \times n_\text{kv heads} \times d_h \times \text{tokens} \times \text{batch}
$$

Multiply by bytes per element (2 for FP16/BF16) to get memory. Notice what's absent: the number of parameters. A model's weights are a fixed cost, but the cache grows linearly with both context length and the number of sequences served at once.

At the default settings a single 8K-token sequence already needs a few gigabytes. Serve 32 of them and the cache dwarfs the weights.

## Why it is a bandwidth problem too

Generating each new token means reading the entire cache from GPU memory once per layer, while doing only a small amount of arithmetic with it. Shazeer observed that this memory traffic, not the arithmetic, dominates incremental decoding time <Cite id="mqa-paper" where="§2" />. Shrinking the cache therefore helps twice: more sequences fit, and each step finishes sooner.

<Callout type="intuition">
Think of the cache as the model's working memory of the conversation so far. Every design on the path from [[mha]] to [[mla]] trades a little modelling flexibility for a smaller working memory.
</Callout>

## Ways to shrink it

- Store fewer key/value heads: [[mqa]] keeps one, [[gqa]] keeps a few groups.
- Store a compressed version and expand it when needed: [[mla]].
- Store fewer bits per number, for example 8-bit cache quantization.
- Store fewer tokens, for example sliding-window or sparse attention.

The first two change the architecture, so they have to be decided before training. The last two can often be applied to an existing model.
