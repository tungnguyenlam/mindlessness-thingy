A [[moe]] layer cuts compute per token by running only $K_r$ of its $N_r$ routed experts, but all $N_r$ expert weight matrices still have to live somewhere. Prior offloading frameworks such as Fiddler <Cite id="fiddler-paper" /> and DAOP <Cite id="daop-paper" /> park inactive experts in system DRAM, which fails on edge desktops where 16 to 64 GB of RAM cannot hold models like Qwen3-30B-A3B (30.3B parameters total, 3.3B active per token <Cite id="qwen3-report" />) <Cite id="flashmoe-paper" where="§1, §2.2" />. FlashMoE moves inactive experts one tier lower to NVMe SSD and pairs per-expert file splitting with a small learned eviction policy that cuts SSD reads <Cite id="flashmoe-paper" where="Abstract, §3" />.

In a [[transformer-block]] with MoE feed-forward layers, the non-expert modules — attention projections, normalizations and routing gates — run on every token and account for only 5 to 7% of the model's parameters <Cite id="flashmoe-paper" where="§2.1" />. FlashMoE separates those non-expert weights from the experts at the file level. Each expert is saved as its own `.pt` file indexed by layer and expert id, bundled with its module class so `torch.load` can read it directly without re-initializing the full model <Cite id="flashmoe-paper" where="§3.1" />.

At startup, only the non-expert file is loaded into memory, with expert MLPs zeroed out in the overridden forward pass <Cite id="flashmoe-paper" where="§3.1" />. During prefill, FlashMoE collects the union of experts routed across the whole prompt batch in a layer, loads each required `.pt` file from SSD once, runs the expert across all its assigned tokens, and scatters the results back by token index <Cite id="flashmoe-paper" where="§3.1, Fig. 3(b)" />. Because distinct routed experts grow sublinearly with prompt length — from 47% of experts at 32 tokens to 67% at 256 tokens — skipping unrouted experts keeps prefill fast <Cite id="flashmoe-paper" where="§4.2" />.

During decoding, FlashMoE pins a fixed cache budget of $C_E$ experts per layer in VRAM according to Equation 1 <Cite id="flashmoe-paper" where="§3.1, Eq. 1" />:

$$
C_E = \left(\text{VRAM}_{\text{size}} - \text{size}_{\text{non-expert}}\right) \times \frac{N_r}{\text{size}_{\text{expert}}}
$$

Here $\text{size}_{\text{non-expert}}$ is the memory taken by non-expert modules, $\text{size}_{\text{expert}}$ is the memory required to store all experts across the model, and $N_r$ ($\text{total\_experts}$) is the number of experts per layer <Cite id="flashmoe-paper" where="§3.1, Eq. 1" />. Because each SSD miss costs roughly 3 ms and expert loading takes over 70% of decoding time, the eviction policy determines decoding throughput <Cite id="flashmoe-paper" where="§3.1, Fig. 5" />.

Belady's optimal replacement policy (MIN) evicts whichever cached item will not be requested for the longest time in the future <Cite id="belady-1966-paper" />. Comparing Least Recently Used (LRU) against Belady's oracle on expert traces exposes two failure modes <Cite id="flashmoe-paper" where="§2.3, Fig. 2" />:

- **Eviction delay:** an expert that was routed once and will not be needed again stays in the cache for 4 to 5 extra decoding steps while its recency ages out <Cite id="flashmoe-paper" where="§2.3, Fig. 2" />.
- **Evicting hot experts:** a frequently routed expert that pauses for a few tokens is evicted right before it is needed again. Within 5 steps of eviction, 34.2% of LRU's evicted experts are re-fetched, compared to 0.1% under Belady's oracle <Cite id="flashmoe-paper" where="§2.3" />.

Overall, Belady reaches an 86% hit rate where LRU reaches about 73%, generating nearly $1.9\times$ as many SSD I/O operations <Cite id="flashmoe-paper" where="§2.3" />. Least Frequently Used (LFU) is no silver bullet either: in head-to-head eviction decisions on Qwen3-30B-A3B, LRU beats LFU 56% of the time and loses 44% of the time, because routing combines short-range bursts with long-range staples <Cite id="flashmoe-paper" where="§2.3" />.

## Approximating Belady with a tiny FFN

<Stepper title="How FlashMoE trains and runs its per-layer ML cache policy">
  <Step title="1. Extract routing traces and Belady oracle targets">
    Run inference on 512 prompts from TriviaQA (up to 512 tokens each) and record which experts each layer routes at every step <Cite id="flashmoe-paper" where="§3.2, Fig. 4" />. From the complete future trace, compute Belady's oracle next-use distance for each expert and normalize the target distances by their maximum <Cite id="flashmoe-paper" where="§3.2, Fig. 4" />.
  </Step>
  <Step title="2. Update and normalize recency and frequency">
    At decoding step $t$, each expert updates its step gap since last use $r_t$ and its cumulative routing count $f_t$ <Cite id="flashmoe-paper" where="§3.2" />. Invert recency as $r_{t,\text{norm}} = 1 / r_t$ and scale frequency by the layer's running maximum as $f_{t,\text{norm}} = f_t / \max(f_t)$, placing both signals in $[0, 1]$ <Cite id="flashmoe-paper" where="§3.2, Alg. 1" />.
  </Step>
  <Step title="3. Predict next-use distance and evict the furthest">
    Concatenate $[r_{t,\text{norm}} \parallel f_{t,\text{norm}}]$ and pass it through the layer's 3-layer, 128-wide SiLU feed-forward network (`ml_cache`) to predict a next-use distance score for each expert <Cite id="flashmoe-paper" where="§3.2, Alg. 1, Tab. 1" />. When a routed expert misses in a full cache, evict the cached expert with the largest predicted distance (`MaxDist`) before loading the new `.pt` file from SSD <Cite id="flashmoe-paper" where="§3.2, Alg. 1" />.
  </Step>
  <Step title="4. Overlap policy evaluation with SSD reads">
    Evaluating the 113 KB cache FFN takes 158 µs on average, whereas reading one expert from the PCIe 5.0 SSD takes roughly 3 ms <Cite id="flashmoe-paper" where="§3.1, §3.2, Fig. 5" />. FlashMoE runs the cache policy asynchronously alongside expert loading so the FFN latency is hidden behind storage I/O <Cite id="flashmoe-paper" where="§3.1, Fig. 5" />.
  </Step>
</Stepper>

At each decoding step $t$, FlashMoE maintains a recency counter $r_t$ (initialized to $\infty$ before an expert is first seen) and a frequency counter $f_t$ for every expert in the layer <Cite id="flashmoe-paper" where="§3.2" />:

$$
(r_t, f_t) = \begin{cases} (1,\; f_{t-1} + 1) & \text{if the expert is routed at step } t \\ (r_{t-1} + 1,\; f_{t-1}) & \text{otherwise} \end{cases}
$$

To feed the policy network, both counters are mapped to $[0, 1]$ so that larger values always mean higher routing likelihood, then concatenated <Cite id="flashmoe-paper" where="§3.2, Alg. 1" />:

$$
r_{t,\text{norm}} = \frac{1}{r_t}, \qquad f_{t,\text{norm}} = \frac{f_t}{\max(f_t)}, \qquad \text{score}_t = \left[r_{t,\text{norm}} \;\|\; f_{t,\text{norm}}\right]
$$

The per-layer policy network $\text{ml\_cache}(\text{score}_t)$ is a 3-layer MLP with hidden width 128 and SiLU activations, trained with mean-squared error against Belady's oracle next-use distances <Cite id="flashmoe-paper" where="§3.2, Tab. 1" />. On a cache miss when the layer's VRAM slots are full, `CacheReplacement` evicts the cached expert with the highest predicted distance score <Cite id="flashmoe-paper" where="§3.2, Alg. 1" />.

On a desktop with an RTX 5070 Ti (16 GB VRAM), a PCIe 5.0 NVMe SSD (7.4 GB/s read) and system RAM locked down to roughly 1 GB of free memory, FlashMoE runs both OLMoE-1B-7B <Cite id="olmoe-paper" /> and Qwen3-30B-A3B <Cite id="qwen3-report" /> across cache budgets of 12 to 24 experts per layer <Cite id="flashmoe-paper" where="§4.1, Tab. 2, Figs. 6–7" />. Where DAOP enumerates combinations of expert placements — tractable for 8-expert models like Mixtral-8x7B, but combinatorially expensive at 64 or 128 experts per layer — scoring each expert with a tiny FFN scales linearly with $N_r$ <Cite id="flashmoe-paper" where="§4.4" />.

<Callout type="pitfall">
The ML cache policy is trained per model from offline routing traces (~2 hours on an A100 for OLMoE-1B-7B), and both training and evaluation in the paper come from TriviaQA splits <Cite id="flashmoe-paper" where="§3.2, §4.1" />. How well a policy trained on question-answering traces transfers to code or long-context reasoning — or to systems where experts already fit in fast DRAM and the 158 µs FFN can no longer hide behind 3 ms SSD reads — is not measured in the paper.
</Callout>
